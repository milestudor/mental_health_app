## Finished application, history and personalization

One Step is a localhost coursework skills prototype for fictional scenarios only. It does not diagnose, provide therapy, assess safety or imply monitoring. It must not be offered, deployed or recommended as something to rely on during a difficult moment. All testing and demonstration use fictional scenarios; no support service was contacted.

The application includes six-cycle 4/6 breathing (60 active seconds), self-paced five-sense grounding, optional check-in, editable fictional profiles, saved activity/conversations, and optional general conversational chat. Application code owns sequence, timing, pauses, immediate Stop, storage and independent support. Grounding requires no written/spoken answers; Next/Skip are explicit, every sense is optional, and completion means only that the sequence ended, possibly with skipped senses. The sensory order follows [NHS inform’s exercise](https://www.nhsinform.scot/healthy-living/mental-wellbeing/breathing-and-relaxation-exercises/grounding-exercises); self-paced controls and skip adaptations are interface decisions, not evidence of clinical effectiveness.

Goals and display choices are explicit, editable and profile-scoped. Saved history can be reviewed and cleared for one profile without deleting another profile’s records or the selected profile’s preferences. Counts are activity records, not progress scores, diagnoses or inferred distress. Optional check-in suggests a simpler view, with an immediate override separate from the saved default. The simpler view reduces home explanation while preserving both skill choices, exits and support. This balances reading effort against explanation without hiding control; reduced human cognitive load remains a design hypothesis, not a measured result.

Live chat answers general questions and follow-ups using the configured model. Reviewed facts constrain app claims; general model knowledge can answer other topics. The browser defaults to no saved profile/activity sharing and offers an explicit opt-in. Up to 12 recent current-conversation messages support follow-ups; older transcripts and check-in notes are excluded from personalization. New chat clears current conversational context without deleting saved history. Replies are bounded to 350 words/4000 characters. There is no browsing/current-information verification, diagnosis, therapy or monitoring claim. General-topic accuracy is not guaranteed.

## Changes from Part 3.1 and resulting decisions

[Design decisions](design/decisions.md) revisit the [Part 3.1 technical plan](design/part3.1-plan.md) and [experience design](design/part3.1-experience.md). Grounding restores the second choice deferred in Part 3.2, but a proposed fixed duration was replaced by self-pacing: reading and sensory access vary, and no timing study supports a universal duration. A second timer was considered and rejected. Screenshot review led to equal desktop skill cards, stacked on narrow screens, with optional check-in below practice. Inferring a recommended exercise from history was rejected because counts do not establish need.

The earlier catalog-only model proposal was expanded at the student’s request to natural general conversation. Mock mode still provides deterministic reviewed fixtures for routine/peer testing; it does not pretend to answer arbitrary topics. The tradeoff is broader generated text with greater semantic uncertainty and possible latency/cost. [Current architecture](design/technical-plan.md) and [chat design](design/general-chat.md) record boundaries, alternatives and evidence. Schema validity alone does not establish relevance or safety. A 50-attempt server cap returns to labeled mocks; the host must keep a session-wide allowance across restarts and use one worker/process.

Crisis-related chat uses a deliberate fixed application boundary and explicit phrase matching to foreground bundled U.S.-labeled support. The match is not assessment: quoted/negated text may trigger it, while indirect wording, spelling variations and other languages can be missed. Personal diagnosis/treatment requests receive boundary copy. The independently labeled support control remains available without a successful API/model result. Opening support pauses exercises; closing it never automatically resumes. Nobody is contacted or monitoring the user. This choice prioritizes independent access while acknowledging classifier limitations.

## Evaluation: mocked checks and actual browser observations

[18 fictional scenarios](evidence/scenarios.md) record expected and observed results, covering ordinary questions, explicit preferences, history, profile isolation, deletion, completed/stopped skills, crisis/negated text, injection attempts and provider failures. [Repeatable scenario code](backend/test_acceptance.py) contains the fictional input strings; [integration checks](backend/test_integration33.py) cover added skill identity. **70 current automated checks pass**, all with mocked/replaced provider transports ([final XML](evidence/final-regression-tests.xml)). Historical 61-check results remain separate. These checks establish selected software behavior, not clinical effectiveness.

Three explicit cross-case behavior checks are documented in [verification](evidence/verification.md): **B1**, simpler display preserves both choices and support; **B2**, opening support pauses and closing requires explicit Resume, while paused grounding cannot advance; **B3**, failed chat/save/model requests preserve support and immediate Stop, with explicit unsaved status/retry. [Browser evidence](evidence/browser-results.json) uses intercepted requests and fictional records, not a real provider outage or support-service contact. Foreground breathing measured about 60.36 seconds, with 60,000 ms persisted active time. Hidden tabs/gaps pause rather than skip unseen time; refresh records interruption and requires a new Start. Earlier full exercise browser evidence remains labeled by scope; later chat UI evidence supplements it.

A surprising finding: baseline HTTP 200 concealed a wrong skill label because the request schema ignored a grounding identifier while SQLite defaulted to breathing. [Baseline readback](evidence/baseline-failure.json), rather than status alone, revealed the defect. A UI-only fix was rejected; the implementation now validates/stores skill identity, rejects mid-session identity changes and renders saved labels. Regression readback verifies the change.

These are documented limits, not hidden requirements deferred without explanation.
