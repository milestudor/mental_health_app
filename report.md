## Finished application and reasoning

One Step is a localhost coursework skills prototype for fictional scenarios only. It does not diagnose, provide therapy, assess safety or imply monitoring. It must not be deployed or offered as something to rely on during a difficult moment. No test uses a real person in distress; no support service is contacted.

The finished flow includes unchanged six-cycle 4/6 breathing, a new self-paced five-sense grounding exercise, optional check-in, editable fictional profiles, profile-scoped saved activity and conversations, and locally available support. Grounding restores the second choice proposed in Part 3.1 but deferred in Part 3.2. Each sense is optional; Next and Skip are explicit, and Pause/Stop stay available. No typed or spoken answers are required. “Completed” means the sequence ended, including skipped senses; it is not improvement. The sensory order is grounded in [NHS inform’s exercise](https://www.nhsinform.scot/healthy-living/mental-wellbeing/breathing-and-relaxation-exercises/grounding-exercises); control/skip adaptations are design choices, not a validated clinical protocol.

[Design decisions](design/decisions.md) revisit the [Part 3.1 technical plan](design/part3.1-plan.md) and [experience design](design/part3.1-experience.md). A fixed grounding duration was replaced by self-pacing because reading and sensory access vary; no human timing study supports a universal duration. The alternative of another timer was rejected. Screenshot review led to two equal desktop cards and moving optional check-in below skill choice. Mobile stacks cards; simpler view hides explanatory copy while preserving both choices. This reduces required reading by design, but human usability benefit remains a hypothesis.

Personalization uses editable preferences and the selected profile’s actual activity counts, with a clear current-view override. Counts do not rank exercises or infer distress. Saved defaults and a temporary simpler-view choice remain separate. Older transcripts and check-in notes are excluded from personalization; bounded current-conversation context supports follow-ups. History can be reviewed and cleared for one profile without deleting its preferences or another profile’s records. Clear labeling matters more than a longer feature list.

The inherited user-requested live conversational adapter differs from Part 3.1’s catalog-only proposal. Mock mode retains deterministic reviewed copy; optional live replies are bounded and grounded in reviewed facts. Schema validity cannot guarantee relevant or safe meaning. [Current architecture](design/technical-plan.md) records this tradeoff. Routine tests and peer sessions default to mocks; the host must enforce at most 50 provider attempts per live session, then return to mocks. A process restart must not reset the host’s allowance. At the code cap the adapter selects mocked catalog text without another provider request.

## Evaluation and findings

[18 fictional scenarios](evidence/scenarios.md) record expected and observed outcomes, including ordinary questions, no-typing preference, history use, profile isolation, deletion, stopped/completed skills, treatment boundaries, crisis/negated text, injection attempts and provider failures. All 61 automated checks passed. [XML](evidence/mock-tests.xml), [browser observations](evidence/browser-results.json), and [verification analysis](evidence/verification.md) distinguish API fixtures from actual browser timing and interactions. These establish deterministic software behavior, not clinical effectiveness.

Three explicit cross-case checks are: **B1**, simpler display preserves both choices and independent support; **B2**, opening support pauses and closing never automatically resumes, while paused grounding cannot advance; **B3**, failed chat/save/model requests preserve independent support and immediate Stop, and saving failure is explicit. Browser request failures were intercepted deliberately; provider timeouts/malformed replies used fixture transports. Actual foreground breathing took about 60.36 seconds; persisted active time was 60,000 ms. No paid model call is included in those results.

A surprising finding was that the original API returned HTTP 200 for a grounding-shaped record but silently saved it as breathing. [Baseline readback evidence](evidence/baseline-failure.json) showed an ignored field combined with a database default. A UI-only label change would not repair history, so the decision was to validate/store `skill_id`, reject identity changes within a session, and render saved labels. Regression readback checks now pass. This illustrates why successful HTTP status alone is insufficient evidence.

A limitation not tested is concurrent tabs clearing and retrying one profile: the in-browser save queue and backend terminal guards do not establish complete multi-tab synchronization. Human usability, screen readers, semantic live-model behavior and other operating systems also remain unverified. Grounding skips are not individually recorded, so completion does not prove engagement.
